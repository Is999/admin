# 库表路由与应用内拆表规范

本方案在 Admin/API 应用内完成物理表路由，在线复制复用 Ghostferry Go 库，不部署 ShardingSphere-Proxy、独立 CDC 或迁移服务。它解决同一 MySQL 主库内的大表水平拆分；跨 MySQL 实例拆库不在本方案范围内。

## 固定逻辑桶

所有 `uid = user.id` 的业务表统一使用：

```text
shard_no = idgen.ShardNo(uid)
         = CRC32(decimal uid string) % 1024
```

- `user` 使用 `idgen.ShardNo(user.id)`。
- 携带 `uid` 的表使用 `idgen.ShardNo(uid)`，禁止裸 `uid % N`。
- `shard_no` 永远位于 `0..1023`，扩容只搬桶，不重算历史桶号。
- 每张表独立配置物理分片数，只允许 `1/2/4/.../1024`。
- 单次在线迁移只允许翻倍；更大跨度必须拆成多轮，确保每张源表每轮只有一个复制区间。
- `user=2`、`user_tag=4` 是合法配置；两表共享桶算法，不要求物理分片数相同。

`user_tag_runtime_uid`、`user_tag_runtime_checkpoint` 和 `user_tag_event_outbox` 有工作流、状态领取或全局清理查询，当前保持单表。只有补齐全部读写和维护路由后，才能把这类运行期表加入物理拆分。

## 稳定物理表名

物理表名使用负责桶区间的起点，已经存在的表名不会因下一次翻倍扩容改变：

| 业务表 | 分片数 | 物理表 |
| --- | ---: | --- |
| `user` | 1 | `user` |
| `user` | 2 | `user`、`user_b0512` |
| `user` | 4 | `user`、`user_b0256`、`user_b0512`、`user_b0768` |
| `user_tag` | 4 | `user_tag_0`、`user_tag_b0256`、`user_tag_b0512`、`user_tag_b0768` |

应用通过 `internal/sharding.Plan` 从固定桶计算表名。禁止业务包自行拼接后缀，也禁止按 `uid % physical_count` 路由。

## 当前路由配置

- Admin/API 的 `user.route_shard_count` 必须同时修改并滚动前完成重启；该字段是启动期配置，热加载只标记需要重启。
- `workflows.user_tag.result_shard_total` 独立控制用户标签结果表数量。
- 用户标签 full 结果写入当前仍显式拒绝执行；`user_tag_0` 已具备独立规划、迁移和表名路由能力，但在真实结果读写调用链补齐前不得执行切流。
- 身份目录只保存稳定的 `user_id/user_shard_no`，不保存会随扩容变化的物理分片数量。
- 登录先查询对应身份目录，校验 `user_shard_no = idgen.ShardNo(user_id)`，再按当前启动配置访问一个用户物理表。
- 后台列表和导出先从身份目录读取有界批次，再按物理表分组执行 `id IN (...)`；不扫描全部物理表，不执行大 offset。

路由配置切换前必须停止 Admin/API 和其他直接写库进程的写流量。不能让旧、新配置实例同时写入，否则相同桶可能被写入不同物理表。

## 新 UID 表准入

新增可拆分 UID 表必须同时具备：

1. 持久化 `shard_no`，创建和批量导入统一调用 `idgen.ShardNo(uid)`。
2. 唯一数字游标，默认使用单列主键 `id`；该字段必须有单列 `PRIMARY KEY` 或 `UNIQUE` 索引。
3. 以 `(shard_no, cursor)` 开头的复合索引，供在线复制和清理做有界范围扫描。
4. 所有单 UID 更新、删除和锁行先计算物理表，并携带 UID、桶或主键条件。
5. 跨用户查询使用目录、汇总表或有资源预算的离线任务，禁止在线广播全部物理表。
6. 评审唯一键边界；单个物理表的唯一索引不自动提供跨表全局唯一。
7. 同步 GORM Model、DDL、配置校验、迁移参数和路由测试。

## 应用内在线扩容

运维入口是 `cmd/tableshard`，固定流程为 `plan → prepare → copy → 切换配置 → 观察 → cleanup`。
除 `plan` 外，执行前必须由秘密管理系统注入 `TABLESHARD_DSN`；不要把迁移 DSN 写进命令参数、脚本或仓库。

### 前置条件

- 源库是可写主库，在线 copy 使用 TCP 连接，MySQL 开启 ROW binlog，`binlog_row_image=FULL`。
- 通过秘密管理系统向 `TABLESHARD_DSN` 注入短期专用迁移账号；命令会校验其网络端点和数据库名与应用写库完全一致。
- `copy` 阶段要求迁移 DSN 显式配置非零 `readTimeout` 和 `writeTimeout`，并传给内嵌复制连接；生产值必须结合单批查询耗时压测，不能短于正常慢批次。
- 专用迁移账号具备源表读取、目标表写入、建表、`LOCK TABLES` 和 binlog replication 权限；线上应用账号不授予这些迁移权限。
- 源表使用 InnoDB 且没有外键；通用命令会直接拒绝外键表。
- 源表不能有触发器；`CREATE TABLE LIKE` 不复制触发器，存在时必须先做表级专项设计，不能绕过门禁。
- 源表结构在全量复制、增量追平和最终校验期间冻结。
- 源表 UID 是正 `int64`，已有正确固定桶，且存在 `(shard_no,id)` 或指定游标的前导复合索引；prepare 和 copy 会先用 `shard_no` 前导索引检查物理表桶范围，再按单个固定桶串行校验 `shard_no = CRC32(decimal uid) % 1024`，避免单条查询扫描整张物理表。该全量数据门禁仍需安排在数据库低压窗口；存量 `user_tag_0` 必须先用在线 DDL 补齐 `idx_shard_id(shard_no,id)`。
- 目标物理表在 copy 前必须为空。失败重跑不得复用部分写入的目标数据，应由 DBA 清空未切流目标表后从头执行。
- copy 期间应用不得直接写目标物理表。

同库复制会同时看到源表和目标表 binlog，因此本实现关闭 Ghostferry 的“独立目标库写入来源检查”；安全边界由目标表未路由、数据库迁移互斥锁和严格空表门禁保证。行复制使用内联指纹，binlog 增量在停写后继续追平并执行最终一致性校验。

### 1. 输出计划

```bash
go run ./cmd/tableshard \
  -action plan \
  -first-table user \
  -from-count 1 \
  -to-count 2
```

用户标签可以独立逐级翻倍；从 1 扩到 4 时先完成 1→2，再以同一流程执行 2→4：

```bash
go run ./cmd/tableshard \
  -action plan \
  -first-table user_tag_0 \
  -from-count 1 \
  -to-count 2
```

### 2. 创建目标表

```bash
go run ./cmd/tableshard \
  -action prepare \
  -f ./etc/config.yaml \
  -first-table user \
  -from-count 1 \
  -to-count 2
```

prepare 会获取数据库级单表互斥锁，检查源表桶范围、字段和迁移索引，通过 `CREATE TABLE ... LIKE` 创建空目标表，再比较源目标真实结构。目标表已存在时只有结构一致且为空才允许继续。

### 3. 在线复制并等待维护窗口

```bash
go run ./cmd/tableshard \
  -action copy \
  -f ./etc/config.yaml \
  -first-table user \
  -from-count 1 \
  -to-count 2 \
  -ready-file /var/run/admin/user-shard.ready \
  -cutover-file /var/run/admin/user-shard.cutover \
  -verified-file /var/run/admin/user-shard.verified
```

copy 会：

1. 按源表合并本轮翻倍迁移区间并启动单个嵌入式 Ghostferry 和 binlog 流；
2. 在线分批复制历史行，同时消费后续 ROW binlog，并再次校验每个增量事件的 UID 固定桶公式后写入目标表；
3. 全量完成且增量接近追平后，以排他方式创建 `ready-file`；
4. 继续同步增量，等待 `cutover-file`；
5. 收到正确的一次性令牌后，获取全部源物理表的数据库只读锁，等待在途写事务结束；
6. 在 `max-downtime` 上限内记录最后 binlog 水位、写完剩余事件并执行最终内联校验；
7. 校验通过后在只读锁仍持有时，以排他方式创建 `verified-file`，随后才释放只读锁。

三个标记路径必须是互不相同的绝对路径，启动时任一路径已存在都会失败，禁止复用旧标记。`ready-file` 是 JSON，包含本轮随机生成的 128 位 `token`；`cutover-file` 的内容必须逐字写入该 token，旧文件或错误令牌都会失败。`verified-file` 绑定本轮 token、数据库目标指纹、表名、UID/固定桶/游标字段、扩容档位和桶迁移计划，是后续 cleanup 的强制凭证。

### 4. 短暂停写和路由切换

看到 `ready-file` 后按以下顺序执行：

1. 网关排队写请求或进入维护页，停止 Admin、API、任务 worker 和其他直写进程。
2. 等待进程优雅退出和数据库在途事务排空。
3. 从本轮 `ready-file` 读取 `token`，先把 token 写入同目录临时文件，再原子重命名为全新的 `cutover-file`；文件只能包含该 token。命令随后获取源表只读锁并完成最终追平和校验。
4. 只有 copy 返回成功且本轮 `verified-file` 已生成后，才把 Admin/API 的 `user.route_shard_count` 一起改为目标值；用户标签则只改 `workflows.user_tag.result_shard_total`。
5. 启动所有实例，执行登录、查询、新增、更新和后台列表冒烟，再恢复入口写请求。

copy 失败时不能切配置。因为旧配置始终只写源物理表，解除维护后可以继续使用旧路由；修复原因并清空未切流目标表后重新执行。

### 5. 观察期和旧数据清理

至少经过一个完整业务峰值和备份周期，确认新路由没有漏读、错误桶、慢查询或目标表异常后，再执行：

```bash
go run ./cmd/tableshard \
  -action cleanup \
  -f ./etc/config.yaml \
  -first-table user \
  -from-count 1 \
  -to-count 2 \
  -verified-file /var/run/admin/user-shard.verified \
  -cleanup-batch-size 1000 \
  -cleanup-delay 100ms \
  -confirm-cleanup 'user:1->2:<verified-file中的token>'
```

cleanup 会先确认应用配置已经是目标分片数，校验 `verified-file` 与当前数据库、表名、UID/固定桶/游标字段、扩容档位和桶计划完全一致，并要求 `confirm-cleanup` 携带该凭证的完整 token；随后在任何删除前检查全部目标表结构和桶范围，再按 `(shard_no,id)` 索引顺序小批删除旧表中已迁移的桶。删除后旧路由不再具备完整数据，回滚必须依赖备份或经过验证的反向迁移，不能直接把配置改回旧值。

自定义 UID 表必须显式传入 `-uid-column` 和真实的 `-active-count`；`user` 默认 UID 字段为 `id`，`user_tag_0` 默认 UID 字段为 `uid`。cleanup 会再次检查目标表 UID 固定桶公式，任何错误数据都会在删除源数据前失败。

观察期内只要回滚过旧路由，或任何进程重新向旧表迁移桶写入，原 `verified-file` 立即失效，禁止 cleanup。必须重新完成正向追平和最终校验并取得新凭证，不能继续使用旧 token。

## 生产门禁

- Admin/API 使用同一 `user.route_shard_count`；发布流水线必须比对两边最终渲染配置，不一致时禁止启动和恢复写流量。
- `user_tag` 等表按自身配置切换，禁止因为 user 已扩容而自动跟随。
- 每次扩容保存 plan 输出、源目标结构、桶分布、Ghostferry 日志、最终校验结果、维护开始结束时间和操作者。
- 监控源库 CPU、IOPS、行锁、连接数、binlog 保留空间和复制延迟；压力超过预算时终止命令，不能继续加并发。
- 资金账变等高一致性表还必须单独评审不可变账本、幂等键、对账和补偿；通用拆表能力不替代资金安全设计。
- 不在 HTTP 请求、普通 worker 或服务启动流程中自动执行建表、复制或清理。
