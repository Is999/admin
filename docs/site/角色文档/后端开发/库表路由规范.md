# 库表路由规范

本文描述 `main` 共享的固定桶与用户物理表运行时路由。默认配置仍使用单表；真正执行在线拆分时，必须选择并遵循对应方案分支的迁移流程，不能只修改路由数量。

## 架构边界

| 层级 | 职责 |
| --- | --- |
| Admin/API | 计算并校验固定逻辑桶，根据当前启动配置定位用户物理表 |
| 身份目录 | 把 username/email/phone/oauth 映射为稳定的 `user_id/user_shard_no` |
| `internal/sharding` | 校验物理分片数并把固定桶映射为稳定表名 |
| 方案分支 | 提供应用内迁移工具，或改由 ShardingSphere-Proxy 管理物理拓扑 |
| MySQL | 保存真实物理表、索引、约束和事务数据 |

身份目录不保存会随扩容变化的物理分片数量。`user.route_shard_count` 只代表当前进程已经完成数据切换的用户物理表数量，不是迁移开关，也不会自动建表或搬迁数据。

## 固定逻辑桶

所有 `uid = user.id` 的业务表使用同一公式：

```text
shard_no = idgen.ShardNo(uid)
         = CRC32(decimal uid string) % 1024
```

- `user` 使用 `idgen.ShardNo(user.id)`。
- 携带业务 UID 的表使用 `idgen.ShardNo(uid)`，禁止裸 `uid % N`。
- `shard_no` 永远位于 `0..1023`，扩容只搬桶，不重算历史桶号。
- 身份目录中的 `user_shard_no` 必须等于 `idgen.ShardNo(user_id)`。
- 物理分片数只允许 `1/2/4/.../1024`，确保每次翻倍时旧表名和固定桶边界保持稳定。

## 用户物理表命名

`internal/sharding.Plan` 使用负责桶区间的起点生成表名：

| 分片数 | 用户物理表 |
| ---: | --- |
| 1 | `user` |
| 2 | `user`、`user_b0512` |
| 4 | `user`、`user_b0256`、`user_b0512`、`user_b0768` |
| 1024 | `user`、`user_b0001` … `user_b1023` |

路由下标为 `shard_no * route_shard_count / 1024`。业务包必须调用模型层路由方法，禁止自行拼接表名、探测表是否存在或在身份目录缓存当前表名。

## 配置与启动边界

- `user.route_shard_count` 默认值为 `1`，Admin/API 必须使用相同值。
- 该字段属于启动路由；热加载发现变化时保留旧值并标记需要重启。
- 配置大于 `1` 前，目标物理表、数据复制、增量追平和一致性校验必须全部完成。
- 路由切换必须停止或排队写流量，并确保没有旧、新配置实例同时写库。
- `main` 只提供运行时路由，不提供在线建表、复制、清理或切流命令。

## 查询规则

### 单用户读写

已知用户 ID 时先通过身份目录取得并校验固定桶，再访问唯一物理表。查询和更新继续携带桶与主键：

```go
db.Table(tableName).Where("shard_no = ? AND id = ?", shardNo, userID)
```

INSERT 必须写入正确的 `shard_no`；UPDATE、DELETE 和锁行不得缺少有界条件。

### 登录查询

1. 根据身份类型查询 `user_identity_username/user_identity_email/user_identity_phone/user_identity_oauth`。
2. 校验 `user_shard_no = idgen.ShardNo(user_id)`。
3. 根据当前 `route_shard_count` 访问一个用户物理表。

禁止登录时扫描全部用户物理表。

### 批量、列表和导出

- 先从身份目录读取有界的 `user_id/user_shard_no` 批次。
- 按目标物理表分组，每张表使用 `shard_no IN (...) AND id IN (...)` 查询。
- 后台分页使用游标和固定批量上限，不允许大 offset、无边界 count 或广播全部物理表。
- 状态、时间等无 UID 条件的跨用户查询必须进入专用目录、汇总表或有资源预算的离线任务。

## 新 UID 表准入

新增可拆分 UID 表必须同时具备：

1. 持久化 `shard_no`，创建和批量导入统一调用 `idgen.ShardNo(uid)`。
2. 至少一个符合真实查询的 `shard_no` 前导复合索引。
3. 所有更新、删除、锁行、重试和清理路径携带分片条件。
4. 明确跨物理表唯一性、事务、一致性和补偿边界。
5. 同步 GORM Model、DDL、配置、迁移参数、测试和文档。

只有“表里存在 UID”不代表可以立即拆分；存在无路由条件的状态扫描、定时清理或 outbox 领取时必须继续保持单表。

## 分支职责

| 分支 | 用户表访问方式 | 扩容方式 |
| --- | --- | --- |
| `main` | 默认单表；运行时已支持按固定桶访问物理表 | 不包含生产迁移命令，不能直接改配置完成拆分 |
| `table-sharding/app-table-sharding` | 与 `main` 使用相同应用内路由 | Admin `cmd/tableshard` 完成同库在线复制、短暂停写校验和清理 |
| `table-sharding/shardingsphere-proxy-alternative` | 应用只访问逻辑 `user` 表 | Proxy 管理物理拓扑，使用该分支独立迁移流程 |

两个方案分支互斥。扩容前必须同时核对 Admin/API 分支、最终渲染配置、数据状态和回滚边界，禁止把应用内表名与 Proxy 逻辑表路由混用。
